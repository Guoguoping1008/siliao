2本次新发现:P0 回归 —— 路由层错误处理失效

2.1 现象(生产实测)

POST   /api/compliance/usage    → 500  Cloudflare 1101 (Worker threw exception)
POST   /api/qa/conversation     → 500  Cloudflare 1101
DELETE /api/qa/conversation     → 500  Cloudflare 1101

返回的不是我们自己的 {"error","message"} JSON,而是 Cloudflare 的未捕获异常页:

{"error_code":1101,"error_name":"worker_threw_exception",
 "detail":"A Worker script ... threw an unhandled exception while processing this request."}

2.2 根因

query/worker/src/interfaces/http/router.ts 的 try/catch 捕获不到 async handler 抛出的错误:

try {
  return handleComplianceUsage(app, req);   // ← 返回 Promise,没有 await
} catch (e) {
  return errorJson("internal", ...);        // ← 永远走不到
}

return promise 时 try 块已经正常返回,catch 不会执行;错误变成 unhandled rejection → Workers 报 1101。

这是 M3 抽路由层时引入的 重构前(index.ts 单文件)是 return json(await app.complianceCheck.check(...)) —— await 在 try 块内,能捕获。M3 把 await 留在了 handler 内部,外层 try/catch 就失去了作用。

2.3 影响面

凡 handler 内部会抛错的端点,全部丢失错误契约:

端点修复前修复后
GET /api/documents1101500 JSON
GET /api/catalog1101500 JSON
GET /api/article/:id1101500 JSON
GET /api/entity/:name1101500 JSON
POST /api/compliance/usage1101500 JSON
POST /api/qa/conversation1101500 JSON
DELETE /api/qa/conversation1101500 JSON
这是它没有早点被发现的根本原因 当前生产上最常见的触发原因就是 D1 表不存在(C1/C1.5 未灌库)—— 所以「1101」实际上一直是「表没建」的表现形式,被这个 bug 掩盖成了 Worker 崩溃。 表面看是环境问题,实际是代码回归。

2.4 修法与验证

修法每个 handler 调用加 await(router.ts 10 处),让错误回到 try 块内走统一 500 JSON 契约
验证新增 router.error-handling.test.ts(7 用例)。修前 6/7 失败(错误逃逸成 unhandled rejection),修后 7/7 通过
回归worker 单测 220 → 227;typecheck 干净
提交e73a4c4 fix(worker): 路由层 try/catch 失效 → 生产 1101 回归
注意 GET /api/search 故意不是 500:检索层多路降级 (FTS5 → phrase → bigram → bge),每路各自 catch,D1 全挂时返回空命中。 这条契约差异已在测试里单独标注。

3唯一阻塞项:D1 灌库需要写权限

3.1 现象

D1 REST API 失败,回退到 wrangler d1 execute
建表失败 —— 需要有 D1 编辑权限的 token

2026-10-28 的 5 次 workflow 运行全部 failure,最后一次尝试后没有再触发。

3.2 已排除的可能

可能排除依据
API 路径写错本地实测 /d1/database/{id}/query 用无效 token 返回 401 Authentication error(不是 404 / No route)
SQL 语法错建表拆成 10 条独立 CREATE TABLE IF NOT EXISTS;且探测步骤的读查询成功
Python 依赖问题抽取步骤成功,脚本能跑
workflow 没注册已修(GitHub 只从默认分支读 workflow);push 触发器已验证生效

3.3 唯一原因

CLOUDFLARE_API_TOKEN secret 没有 D1 编辑权限。

这与 docs/deployment-info.md 的记录完全一致:

/d1/database → ⚠️ 401 —— 部署不需要,D1 数据是一次性灌的
没给 D1 权限是有意的 —— 最小权限原则

那个 token 是故意做成最小权限的(部署只需写 Worker/Pages)。而灌 D1 是另一类操作。

3.4 需要你做的(约 3 分钟)

① 建 Token→ ② 权限 Account → D1 → Edit→ ③ TTL 留空→ ④ gh secret set CLOUDFLARE_D1_TOKEN→ ⑤ 我改 workflow 并触发灌库
TTL 必须留空 OAuth token 1 小时就过期、refresh_token 每次刷新都轮换。 本地 wrangler token 也已过期(9109 Invalid access token,refresh 报 invalid_grant), 所以本地走不通,只能靠 CI + 一个有 D1 权限的永久 token。

3.5 拿到 token 后的执行序列

# ① 建 C1.5 的会话表(必须单独跑)
npx wrangler d1 execute siliao-db --remote --file ./query/worker/migrate_c15.sql

# ② 建 C1 的合规表 + 灌数据(走 CI 的 seed-compliance workflow)
gh workflow run seed-compliance.yml
不能重跑 schema.sql migrate_c15.sql 与 migrate_c1.sql 都必须单独跑 —— 生产库有 3145 条条文,wrangler 4.127+ 对「schema 变了」的库报 D1_RESET_DO,会清空远端表。
