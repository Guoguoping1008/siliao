ADR-004 · Domain-Driven Design

DDD 系统架构：五个限界上下文

把「饲料法规智能体」从 1059 行单文件 Worker 重构为 按业务语义划分的限界上下文。 核心主张：按领域划分，而不是按技术分层 —— 经典 DDD 的全套仓储/工厂/规格在 Serverless 栈上换不来可测性收益， 但「规则引擎该放哪、变更监控归谁管」这个问题必须现在解决，否则对档方案开工就是第二遍同样的混乱。

1重构动因：三个结构性负债

当前系统能跑、指标达标（recall@10 76.0% / MRR 0.647），但存在三个结构性负债：

负债具体表现触发场景
L1 · 关注点混杂 路由分发、检索算法、LLM 调用、引用校验、D1 SQL 全部平铺在一个文件，26 个函数无模块边界 改检索逻辑要读懂 RAG 逻辑；改 prompt 怕碰坏检索
L2 · 语义无边界 6 组表 + articles_fts 共处一个 schema，没有「这是哪个领域的模型」的概念 无法界定「规则库该放哪张表」「案例库归谁」
L3 · 能力扩展无落点 方案文档里的规则引擎 / 变更监控 / 审核预审 / 案例库，加任何一项都只能继续往 index.ts 塞函数 对档方案（4–6 周）开工即失控
关键判断 L1/L2 是代码组织问题，值得现在修；L3 是架构容量问题，必须现在修 —— 否则对档方案开工就是第二遍同样的混乱。

但：DDD 在这个项目有真实风险 —— 技术栈是 Cloudflare 全 Serverless（Workers + D1 + Pages），没有 JVM、没有应用服务器、没有 DI 容器。 经典 DDD 的「聚合根 / 仓储 / 领域服务 / 防腐层」若照搬成目录结构，会变成换皮：目录分了，依赖还是乱的。

切分依据是「法规的什么性质决定它归谁管」，而非技术分层。

⑤法规监测支撑域
Monitoring

RegulationRelease（公告 + 差异 + 影响评估）

待建 对档方案 M4 阶段，按需展开

为什么这样切

  • ① 与 ② 分离 —— 法规原文是事实（不可变），限量规则是判定依据（可随公告更新）。把两者混在一起，改规则就会碰到正文。
  • ③ 是编排者不是领域 —— 问答不拥有任何业务数据，它只调用 ①②④ 并整合。这是「支撑域」的标准形态。
  • ④ 暂不投 —— 图谱能力（关系推理）对当前「找条款」场景收益不明，而运维成本（索引重建 + 增量维护）不低。先留接口，不投实现。
  • ⑤ 用事件解耦 —— 只读核心域 ① 的写入只能由外部版本变更驱动，事件表达最自然。

3依赖规则（强制）

R1上下文间只经 ACL 通信 —— 禁止跨上下文直接 JOIN 对方表。② 要读条文原文，必须经 RegulationRepository + ACL，不得 SELECT ... FROM articles
R2依赖方向单一 —— ③ → ①②④；⑤ --事件--> ①。禁止 ① → ③（核心域不知道被谁调用）
R3外部系统一律 ACL —— LLM / bge / 政府网站全部经防腐层。领域层不得出现 fetch()
R4只读核心域 —— ① ② 的表只允许经由各自仓储写入，禁止跨上下文写
R5领域服务不依赖框架 —— ComplianceEvaluator / CitationValidator 不得 import Workers/D1 类型
违反即 code review 打回 这五条不是文档约定，是可以用测试自动校验的规则 —— 见第 10 节「架构测试」。

4分层与 Serverless 适配

接口层 Interface
Controllers / DTO / 防腐层 ACL
  • HTTP 路由 · 请求校验 · 响应组装 · 外部系统防腐层
应用层 Application
Use Cases / Orchestration —— 编排，不写业务规则
  • InquiryService · ComplianceCheckUseCase · ReleaseDetectUseCase
★ 领域层 Domain
Entities / ValueObjects / Services —— 纯 TS，零框架依赖，零 I/O，100% 可单测
  • RegulationDocument · ComplianceRuleSet · Entity
  • ComplianceEvaluator · CitationValidator —— 两条核心业务规则都在这层
基础设施层 Infrastructure
Repositories / Adapters
  • D1Repository 实现 · bgeClient · llmClient · 爬虫适配器

Serverless 适配说明

经典 DDD本项目适配理由
Spring DI 容器手写 Composition Root（index.ts 顶层 new 出所有仓储/服务）Workers 无 DI 容器；手写反而更透明，依赖关系一眼可见
Repository 接口 + 实现分离接口放 domain 层，实现放 infrastructure领域层可 mock，测试不碰 D1
领域事件总线Workers ctx.waitUntil() + 简单事件分发不引入外部 MQ；事件量小
数据库事务D1 单库 + 单次 batchD1 不支持跨表事务，领域边界设计已规避此需求

6数据所有权与表归属

表归属上下文写权限
documents / chapters / articles① 法规知识库仅 ① 的仓储（经 ⑤ 事件触发）
articles_fts① 法规知识库同上（FTS 影子表）
catalog① 法规知识库同上（书籍原版层级）
compliance_rules / rule_versions② 合规规则仅 ② 的仓储 待建
entities / entity_articles④ 知识图谱仅 ④ 的仓储
index_meta④ 知识图谱仅 ④ 的仓储
regulation_releases / subscriptions⑤ 法规监测仅 ⑤ 的仓储 待建
⚠️ 发现一处现存的跨上下文外键 entity_articles 对 articles 有外键约束 —— 这是跨上下文外键，违反 R1。

修正方案：图谱上下文改为存 article_ref（逻辑引用，不带 FK），由 ACL 在读取时解析。 这样 ④ 可以独立演进，且将来 ① 换存储不影响 ④。

事件发布者消费者载荷

RegulationVersionIngested① 知识库② 合规规则需要重算规则的条文 id 列表

8现状 → 目标映射（可执行）

M1 · 1 天
抽离领域层 —— 不改变任何行为
把纯逻辑从 index.ts 抽到 domain/，建立第一批单测。
映射：validateCitations → domain/inquiry/citation-validator.service.ts； buildRagPrompt → application/inquiry/prompt-builder.ts； llmConfig+fetchWithRetry → interfaces/acl/llm.acl.ts； plainExcerpt → interfaces/acl/regulation.acl.ts； r2Key → infrastructure/persistence/d1/mappers.ts
验收：现有 34 个单测保持绿 + 新增领域层单测 ≥ 20 个 + CI eval 门禁 recall@10 ≥ 70% 不变
M2 · 3–5 天
建合规规则上下文 —— 快档核心
交付：compliance_rules 表 + 仓储 + ACL；ComplianceEvaluator 领域服务（纯函数，100% 单测覆盖）； POST /api/compliance/usage 端点；前端「用量合规速查」输入框
验收：50 条真实限量规则入库 → 输入「维生素C + 猪 + 200mg/kg」返回「合规 + 依据条款原文」； 超限量返回「超限 + 超出量 + 依据条款」；未覆盖物质返回「规则未覆盖，需人工确认」（不允许返回合规）
M3 · 3–4 天
领域层与基础设施层彻底分离
交付：index.ts 从 1059 行 → < 150 行（仅剩 composition root + 路由挂载）； 全部 D1 SQL 移入 infrastructure/persistence/；领域层引入 domain/ 后单测覆盖率门禁
M4 · 按需
拆第五上下文 —— 对档方案
⑤ 监测（爬虫 + 差异检测）落地时，才建 monitoring/ 上下文与事件机制。不提前造。

9取舍：否决了什么

方案优点缺点选择
按领域划分上下文 + DDD 分层（本方案） 边界对齐业务语义；规则引擎/监测有明确落点；领域层纯函数可单测 1059 行拆成 ~40 文件，短期可读性下降，需靠目录约定与 barrel 导出缓解 采用
继续单文件 + 加注释分区 零迁移成本 L3 必然失控，对档方案开工即第二遍混乱 否决
照搬经典 DDD（仓储/工厂/规格全套） 教条完整 Workers 无 DI 容器，大量样板代码换不来可测性收益 否决
全面迁移 FastAPI + PostgreSQL + Milvus
（架构方案文档原选型）		 匹配 DDD 成熟范式；支持事务/向量库 放弃 Serverless 零运维优势；需服务器 + 迁移 3145 条文 + 重建索引；违本项目最大优势 否决
只做分层不做上下文划分 改动小 规则库/监测归属仍不清，L3 未解决 否决
被否决方案值得记录的原因 架构方案文档（第 7 章）假设 FastAPI + Redis + PostgreSQL。实际落地用了 Cloudflare 全 Serverless， 这是受约束下的正确偏离（零运维、零付费产品开通、CI 推代码即上线）。 DDD 重构不改变这个技术栈 —— 它是在现有栈内调整代码组织，不动运行时形态。

10风险与应对

风险等级应对
DDD 换皮：目录分了，依赖还是乱的高R1–R5 五条强制规则写进 code review checklist；用依赖方向测试（架构测试）自动校验
拆文件引入行为回归中M1 阶段严格零行为变更，用现有 34 单测 + 9 e2e + CI eval 门禁三重护栏
领域层被基础设施污染（偷偷 import D1）中架构测试：扫描 domain/ 目录的 import，发现 D1Database 等即失败
只读核心域与「新增法规」流程冲突低写入统一走 ⑤ 的领域事件；① 的仓储提供 ingestRelease() 内部方法
过度设计：为不存在的需求建上下文中④ 图谱保持空壳不实现；⑤ 不到需求不建。按需展开
团队不熟悉 DDD中通用语言表放进代码注释与本文档；context 划分先用 3 周验证再推广

预期产出

  1. 5 个限界上下文，每个有明确的通用语言、聚合根、不变量与依赖规则
  2. 领域层纯 TS 零依赖，100% 可单测，不碰网络不碰数据库
  3. 规则引擎有了确定归属（② 合规规则），快档方案可直接开工
  4. index.ts 从 1059 行瘦身到 <150 行，新人可读
  5. 架构测试自动守护依赖方向，DDD 不靠人的自觉维持
下一步 M1（抽离领域层，1 天）是零风险起步 —— 不改行为，只搬代码 + 补单测。 M2（合规规则上下文）才是快档方案的技术落点。

建议顺序：M1 → M2 → M3，M4 留到对档方案启动时。
