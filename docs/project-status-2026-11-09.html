2.1 P0 · 业务阻断 合规速查全线返回 not_covered

D1 实测：

生产实测（POST /api/compliance/usage，参数齐全）：

{"status":"not_covered","matchedSubstance":null,"ruleHits":[],

这不是故障，是安全闸门按设计工作 —— 未审核规则不参与判定。但业务效果等价于「功能不可用」：用户查「猪饲料维生素C 限量 200mg/kg」，不论超限还是合规，一律回 not_covered。

值得肯定的是返回体诚实地附了 coverageGap.reason + relatedArticles（回落到《饲料和饲料添加剂管理条例》第二十五条原文），没有静默失败。但 matchedSubstance: null 说明连物质名都没匹配上 —— 这是规则闸门拦在匹配之前的结果，符合设计。

2.2 P1 · 体验劣化 问答延迟从 11s 劣化到 37-63s

生产实测 4 次 POST /api/qa：

try1: HTTP 200 time 47.2s
try2: HTTP 200 time 63.1s
try3: HTTP 200 time 37.5s
try4: HTTP 200 time 48.4s   (elapsed_ms = 45974)

根因（11-09 三个提交引入）：旧模型 MiniMax-Text-01 被 provider 下线，换成 MiniMax-M3.1-Flash —— 这是 reasoning 模型，响应分两段：

  • reasoning_content —— 思考过程
  • content —— 最终答案

两者共用 max_tokens 配额。max_tokens=1000 时 reasoning 吃掉全部预算导致答案整段变空，于是提到 16000 —— 预算够了，代价是推理段本身就要花 20-40 秒。

query/worker/src/interfaces/acl/llm.acl.ts:98-127 有完整的实测记录：

| max_tokens | 正确 | 空答案 | reasoning 实际长度 |
权衡：这是「换活模型」换来的延迟成本，不是 bug。当前可以接受（40-60s 对法规问答这类重推理场景尚可），但没有 P95 指标、没有超时告警，一旦用户量上来或 provider 再变，会静默劣化。

建议（择一）：

  • 快档：保留 reasoning 模型，但加 reasoning_content 长度上限 / 超时熔断，超过阈值降级到非 reasoning 模型。改动小（~半天），保住正确性。
  • 对档：换非 reasoning 模型，延迟回 10-15s，但需重跑引用准确率 eval 确认质量不降。

八 · 已踩过的坑（别重蹈）
  1. return promise 不会进 try/catch —— 必须 return await promise。M3 抽路由层时丢了 await，生产报 1101，根因是 D1 报错被掩盖成 Worker 崩溃。
  2. .gitignore 行内注释不生效 —— Images/ # 说明 整行都是匹配模式，曾提交 510 张扫描图（3.2GB）。注释必须单独占一行。
  3. 不能重跑 schema.sql —— 生产库 3145 条条文，wrangler 4.127+ 对「schema 变了」的库报 D1_RESET_DO，会清空远端表。用 migrate_c1.sql / migrate_c15.sql 单独跑。
  4. 不要用 wrangler OAuth token 跑 CI —— 1 小时过期且 refresh_token 每次轮换。
  5. SQLite 的 LIKE 对中文无效 —— 实测 ?q=维生素 → 0 条。改用 instr() → 15 条。换回 LIKE 不会报错，只是永远搜不到东西。
  6. eval 不指定公网 BGE 地址会静默退化 —— 看着像指标掉了，实际没测到 hybrid。
  7. reasoning 模型 max_tokens 与 content 共用配额 —— 给太小答案整段变空，给太大延迟劣化到 40-60s。
