## 0. 摘要

构想稿提出「RAG + 知识图谱 + 规则引擎三者互补」，覆盖四大功能模块。
本文把这份构想落到**可排期的功能**，并给出每一项的**真实数据基础与可行性实测**。

### 核心结论

| 结论 | 内容 |
|---|---|
| **能力边界** | 当前系统是**纯 RAG 检索问答**。构想稿的「合规判定」需要规则引擎，**尚未存在** |
| **数据可得性** | 限量表可**确定性抽取**。实测 6 个文件抽出 **28 条 (物质×动物×限量) 三元组** |
| **最大落差** | 「款/项」粒度未建模 —— 一条含「猪 A、家禽 B、水产 C」的条文无法只引用其中一项 |
| **落地顺序** | ① 法规检索 → ② 合规审查（用量速查）→ ③ 标签审查 → ④ 风险预警 → ⑤ 知识问答增强 |

### 一句话判断

> **构想稿是对的，但它的实现顺序应该是「先做能做的，再做需要新数据的」。**
> 法规检索与知识问答已上线；合规审查的核心（用量判定）**现在就能做**；
> 而版本追溯、抽检预警、合规日历**都需要新数据源**，不能靠现有语料变出来。

## 2. 数据基础实测 —— 一切设计的前提

功能能不能做，取决于**数据在不在、能不能确定性地取出来**。以下全部是本次实测结果。

### 2.1 语料概览

```
1021 页扫描件 → OCR → minimax/ 三层树
196 文档 / 529 章 / 3145 条文
顶层目录: 01法规(1) · 02制度文件(139) · 03相关法律法规文件(32) · 04标准及标准目录(5) · 封面/目录(2)
```

### 2.2 表格数据可解析性（300 个含表格文件）

| 指标 | 实测值 | 含义 |
|---|---|---|
| 含表格文件 | **300** | OCR 表格保留为 HTML `<table>` |
| 表格总行数 | 4818 | — |
| 有效数据行 | **4291（89.1%）** | 剔除 `—` 空行后的真实内容 |
| **列宽一致的文件** | **256 / 300（85%）** | ✅ 表头可定位，列语义可识别 |
| 含「数值+单位」的行 | 137（占有效行 3.2%） | 限量类数据集中在这少数文件 |

> **结论**：表格结构**总体可靠**（85% 列宽一致），
> 但含数值+单位的行只占有效行的 3.2% —— 数值要么在长句里（`猪150～300mg/kg`），
> 要么在「质量指标」列（`粗蛋白质≥50%`）而非限量列。**必须列感知，不能全表正则。**

### 2.3 限量三元组抽取可行性（确定性解析器实测）

| 指标 | 实测值 |
|---|---|
| 抽出 (物质×动物×下限~上限×单位) | **28 条** |
| 涉及文件 | **6 个**（全在 `46_饲料添加剂安全使用规范`） |
| 涉及顶层目录 | `02制度文件` |

**实测样本**（`0324.md`，维生素C）：

```
物质: L-抗坏血酸(维生素C)
  猪      150～300 mg/kg
  家禽     50～200 mg/kg
  犊牛    125～500 mg/kg
  蛙类    100～150 mg/kg
  鲤鱼    300～500 mg/kg
```

**这个数字是本设计的锚点** —— v1 规则库按 **30–50 条** 估算，不多不少，
手工校核完全可行，且**每条都有原文出处可溯源**。

### 2.4 真实存在的 5 种写法（解析器必须覆盖）

| # | 原文形态 | 示例 | 难点 |
|---|---|---|---|
| 1 | `动物+范围+单位` | `猪150～300mg/kg` | 基础 |
| 2 | 带冒号 | `猪：0.15 ～0.5 mg/kg` | 全角/半角冒号 |
| 3 | **多动物并列 + 阶段** | `罗非鱼、鲶鱼—鱼苗300mg/kg—鱼种200mg/kg` | 一个动物对应**两个阶段值** |
| 4 | **括号内嵌套** | `猪30～50mg/kg(乳猪300～500mg/kg)` | 括号是**例外**，不是主值 |
| 5 | **多物质共用一条** | `同时使用时，在配合饲料中的总量不得超过150mg/kg` | 约束对象是**组合**不是单体 |

> **格式 4 是必须做对的**：括号内的 `乳猪300～500` 是**乳猪阶段的独立上限**，
> 不能被当成 `猪30～50` 的一部分，也不能丢弃。
>
> **格式 5 是必须排除的**：`总量不得超过150mg/kg` 不针对单一物质，
> 抽取时必须**标记为组合约束**，否则会算错。

### 2.5 禁用清单可抽取性（文本型）

| 关键词 | 命中文件数 | 说明 |
|---|---|---|
| 标签 | 125 | ✅ 可做标签审查 |
| 生产许可证 | 88 | ⚠️ 只有**条款**，无**实际证件数据** |
| 有效期 | 86 | ⚠️ 同上 |
| 批准文号 | 65 | ⚠️ 同上 |
| 禁用 | 39 | ✅ 可做禁用清单 |
| 禁止使用 | 24 | ✅ |
| 不得使用 | 18 | ✅ |
| 休药期 | 23 | ✅ 可做停药期规则 |

> **关键区分**：「生产许可证」在语料里是**法规条款**（规定许可证怎么办理），
> **不是**企业的实际许可证数据。企业资质审查需要**外部数据源**，靠语料做不了。

### 2.6 语料里已存在的「非饲料」法规

`03相关法律法规文件` 32 份含：《兽药管理条例》《新兽药注册办法》《兽药标签和说明书管理办法》等。

> 方案文档第十章说规范「可复用到兽药领域」—— 但语料里**已经有兽药法规**，
> 只是没做领域标记。`documents` 表**无 `domain` 字段**，现在只能靠目录名硬编码。

## 3. 功能一：法规检索模块（90% 已上线）

### 3.1 已实现

| 子功能 | 实现 | 状态 |
|---|---|---|
| 语义检索 | D1 FTS5（phrase 优先 + bigram RRF + 标题加权）⊕ bge-m3 语义 | ✅ |
| 层级导航 | 书籍原版层级 + 文号 + 起始页（`/api/catalog`） | ✅ |
| 全文命中 | `recall@10 76.0%` / `MRR 0.647` / 业务 query `MRR 0.717` | ✅ |

### 3.2 待补：版本追溯（需新数据）

构想稿要求「展示法规的历史修订记录与现行有效版本」。

**当前障碍**（两项都缺）：

1. **`articles` 表无状态字段** —— 不知道某条是否已废止/被修订
2. **无修订历史数据** —— 语料是「2026 版汇编」，只有现行版本，没有历史快照

**数据模型补齐方案**：

```sql
ALTER TABLE documents ADD COLUMN status TEXT DEFAULT 'effective';
-- effective | superseded | draft | repealed

ALTER TABLE documents ADD COLUMN supersedes_doc_id TEXT;
-- 被本文档取代的上位文档

ALTER TABLE articles ADD COLUMN version_snapshot TEXT;
-- 该条文所属的法规版本标识
```

**但即使加了字段，历史仍为空** —— 真正的版本追溯需要：

| 来源 | 可得性 | 说明 |
|---|---|---|
| 现行法规的**修订说明**章节 | 🟡 语料里可能有 | 《条例》的「根据XX年修订」表述 |
| 历史版本 PDF | ❌ 需采购/爬取 | 农业农村部不提供结构化历史 |
| 变更时间线 | ❌ 需 ⑤ 监测上下文 | 只能记录**上线之后**的变更 |

**结论**：版本追溯**第一期只能做到「标注当前版本 + 标注被取代关系」**，
真正的历史回溯要等 ⑤ 落地后逐步积累。

> **建议**：把它从「功能」降级为「数据字段」，先补 `status` / `supersedes_doc_id`，
> 让 ⑤ 落地时**有地方可写**。这是 ADR-005 指出的「知识时效可审计」原则的技术前提。

### 3.3 待补：领域标记（低成本高价值）

```sql
ALTER TABLE documents ADD COLUMN domain TEXT DEFAULT 'feed';
-- feed | veterinary | pet_food | general
```

- `01法规` / `02制度文件` → `feed`
- `03相关法律法规文件` → 需人工分类（其中兽药类 → `veterinary`）
- `04标准及标准目录` → `feed`

**收益**：支持「只查兽药法规」「排除通用法规」等过滤，
并为「可复用到其他垂直领域」这个目标留出数据基础。

## 4. 功能二：合规审查模块（30%）

这是构想稿的**核心价值主张**，也是当前**最大的能力缺口**。

### 4.1 构想稿的原始设想

```
用户提问："这种预混料在猪饲料中的添加量合规吗？"

Step 1 意图识别  → 识别为"合规审查"，提取实体：产品类型=预混料、动物种类=猪、属性=添加量
Step 2 任务拆解  → 子任务1 检索适用条款 / 子任务2 查该动物阶段上限 / 子任务3 比对是否超标
Step 3 工具调用  → 向量检索 + 知识图谱 + 规则引擎
Step 4 结果融合  → 法规原文 + 阈值数据 + 比对结果
Step 5 输出生成  → 合规/不合规 + 依据条款 + 建议调整范围
```

### 4.2 落地映射 —— 每一步落到哪个组件

| 构想稿步骤 | 落地实现 | 状态 |
|---|---|---|
| Step 1 意图识别 | `POST /api/compliance/usage` 的**结构化入参**替代 LLM 意图识别 | 🟡 设计变更 |
| Step 2 任务拆解 | **单步判定**，无需 Planner（一个物质×一个动物 = 一次比对） | ✅ 简化 |
| Step 3a 向量检索 | `HybridRetriever`（已上线） | ✅ |
| Step 3b 知识图谱 | **改为「目录表查询」**（见下） | 🟡 设计变更 |
| Step 3c 规则引擎 | `ComplianceEvaluator`（**新建**） | ❌ |
| Step 4 结果融合 | `ComplianceVerdict` 值对象 | ❌ |
| Step 5 输出生成 | 固定模板 + 依据条款原文 | ❌ |

### 4.3 关键设计变更 ①：不用知识图谱查「是否在目录内」

构想稿说「调用知识图谱：查询该产品是否在《饲料添加剂品种目录》中」。

**但这个问题不需要图谱** —— 它是一个**集合成员判断**：

```
「L-抗坏血酸(维生素C)」 ∈ 《饲料添加剂品种目录》
```

《饲料添加剂品种目录》在语料里是 `02制度文件/04_（四）使用管理/45_饲料添加剂品种目录/`，
含 23 个表格行。抽成一张 `substance_catalog` 表后，**一次 SQL 精确匹配**即可。

> **为什么不用图谱**：图谱解决的是**多跳关系推理**（A→B→C）。
> 「查某物质在不在目录里」是**单跳集合查询**，上图谱是杀鸡用牛刀，
> 而且图谱当前是**空表**（`entities` 实测为空）。
>
> **保留图谱的价值在于**：跨法规的**交叉引用关系**
> （如「本条依据《条例》第X条」），那是**审核预审**场景的需求，不是用量判定。

### 4.4 关键设计变更 ②：意图识别改为结构化入参

构想稿设想 LLM 做意图识别 + 实体抽取。**但用量判定不该走 LLM**：

| 走 LLM 的问题 | 走结构化接口的问题 |
|---|---|
| 「预混料」是产品类型还是物质名？LLM 可能抽错 | 入参就分好了字段 |
| 「200」是 mg/kg 还是 g/kg？LLM 会猜 | 单位是必填字段 |
| 抽错了用户看不出来，还以为得到了结论 | 参数错直接 400 报错 |

**结论**：用量判定**必须是确定性接口 + 确定性判定**。
LLM 只在**用户不知道自己要查什么**时帮忙（自然语言 → 建议查询），不参与判定本身。

> 这正是方案文档「规则与模型双轨」原则的落地：
> **量化硬约束用确定性规则引擎，语义判断用 LLM，二者冲突时以规则为准。**

### 4.6 领域服务：`ComplianceEvaluator`

```ts
// domain/compliance/compliance-evaluator.service.ts

export type VerdictStatus = 
  | "compliant"      // 合规
  | "exceeded"       // 超限
  | "prohibited"     // 禁用
  | "not_covered";   // ⚠️ 规则未覆盖 —— 必须显式出现

export interface ComplianceVerdict {
  status: VerdictStatus;
  /** 每条被命中的规则，带原文出处 */
  ruleHits: RuleHit[];
  /** 若超限，给出建议调整范围 */
  suggestion?: {
    maxAllowed: number;
    unit: string;
    message: string;
  };
  /** 若未覆盖，说明覆盖缺口 */
  coverageGap?: {
    reason: string;
    /** 检索到的最相关条文（供人工参考） */
    relatedArticles: RelatedArticle[];
  };
}

export interface RuleHit {
  ruleId: string;
  sourceArticleId: string;
  sourceDocId: string;
  sourceExcerpt: string;
  limit: { min?: number; max?: number; unit: string };
}
```

**判定逻辑**（纯函数，100% 可单测）：

```ts
export function evaluate(
  usage: UsageDeclaration,
  rules: ComplianceRule[],
  catalog: SubstanceCatalog | null
): ComplianceVerdict {
  // 1. 禁用规则优先 —— 禁用是硬红线, 无条件拒绝
  const prohibition = rules.find(r =>
    r.rule_type === "prohibition" && matches(r, usage));
  if (prohibition) {
    return { status: "prohibited", ruleHits: [toHit(prohibition)] };
  }

  // 2. 限量规则
  const limits = rules.filter(r =>
    r.rule_type === "limit" && matches(r, usage));

  // 3. ⚠️ 无命中 → 必须返回 not_covered, **禁止返回 compliant**
  if (limits.length === 0) {
    return {
      status: "not_covered",
      ruleHits: [],
      coverageGap: {
        reason: "规则库未覆盖该物质/动物组合, 需人工确认",
        relatedArticles: [],   // 由调用方经检索补齐
      },
    };
  }

  // 4. 比对 —— 取所有命中规则中最严的一条
  const strictest = limits.reduce((a, b) =>
    (b.max_value ?? Infinity) < (a.max_value ?? Infinity) ? b : a);

  if (usage.value > (strictest.max_value ?? Infinity)) {
    return {
      status: "exceeded",
      ruleHits: limits.map(toHit),
      suggestion: {
        maxAllowed: strictest.max_value!,
        unit: strictest.unit,
        message: `超出上限 ${usage.value - strictest.max_value} ${strictest.unit}`,
      },
    };
  }
  // 5. 低于下限
  if (strictest.min_value !== undefined && usage.value < strictest.min_value) {
    return { status: "exceeded", ruleHits: limits.map(toHit),
      suggestion: { maxAllowed: strictest.max_value!,
        unit: strictest.unit,
        message: `低于下限 ${strictest.min_value - usage.value} ${strictest.unit}` } };
  }

  return { status: "compliant", ruleHits: limits.map(toHit) };
}
```

#### ⚠️ 两条不可协商的不变量

| # | 不变量 | 依据 |
|---|---|---|
| **1** | **规则未覆盖时必须返回 `not_covered`，绝不能返回 `compliant`** | 「合规优先」+ 风险表「规则覆盖不全造成漏检」 |
| **2** | **每条规则必须绑定 `source_article_id`**，无出处不允许入库 | 「涉及监管结论的输出必须可溯源（条款号+原文）」 |

> **不变量 1 的实现细节**：`evaluate()` 里「无命中 → return not_covered」这一分支
> 必须有**单测锁死**，且用**故意构造的未覆盖物质**测。
> 这类 bug 极容易在后续重构中被"优化"掉。

### 4.8 命名匹配策略（工程难点）

用户输入的「维生素C」与规则库里的「L-抗坏血酸(维生素C)」**对不上**。

**三级匹配，依次降级**：

| 级别 | 策略 | 示例 |
|---|---|---|
| 1 | **精确匹配** `name_cn` | `L-抗坏血酸(维生素C)` → 命中 |
| 2 | **括号别名** | `维生素C` → 从 `L-抗坏血酸(维生素C)` 的括号里提取 → 命中 |
| 3 | **别名表** `substance_alias` | `维生素C` / `Vitamin C` / `Ascorbic acid` → 命中 |

```ts
export function matchSubstance(
  input: string,
  catalog: SubstanceCatalog[]
): { match: SubstanceCatalog; method: "exact" | "alias" | "fuzzy" } | null {
  // 1. 精确
  const exact = catalog.find(c => c.name_cn === input);
  if (exact) return { match: exact, method: "exact" };

  // 2. 括号内别名 —— 「L-抗坏血酸(维生素C)」的括号内容
  for (const c of catalog) {
    const m = c.name_cn.match(/[（(]([^）)]+)[）)]/);
    if (m && m[1] === input) return { match: c, method: "alias" };
  }

  // 3. 别名表
  const byAlias = catalog.find(c =>
    c.name_en?.toLowerCase() === input.toLowerCase());
  if (byAlias) return { match: byAlias, method: "alias" };

  return null;  // ⚠️ null → not_covered
}
```

> **不做模糊匹配**：向量相似度匹配出来的「维生素C ≈ 抗坏血酸钙」在合规判定里是
> **危险**的 —— 抗坏血酸钙和抗坏血酸的限量完全不同。
> **宁可说「未覆盖」，不可猜。**

### 4.9 禁用清单（规则类型 `prohibition`）

从 39 个含「禁用」的文件的条款文本抽取。

**典型条款形态**（实测）：

> 「严禁在自配料中添加禁用药物、禁用物质及其他有毒有害物质。」
> 「不得在饲料生产过程中进行维修、焊接、气割等作业。」← **这条不是禁用物质！**

> ⚠️ **抽取时必须人工剔除假阳性**。上例第二条明显是「生产操作禁令」
> 而非「物质禁用」。这正是 `review_status` 字段存在的理由：
> **自动抽取 → 人工审核 → 才能生效**。

**流程**：

```
自动抽取候选 ──→ review_status='pending'
      │
      ├── 人工审核 ──→ 'reviewed' (生效) / 'rejected' (剔除)
      │
      └── 判定时只读 review_status='reviewed' 的规则
```

> **未审核的规则不参与判定** —— 这是防止「LLM/正则抽错了直接给用户错误结论」的关键闸门。

### 4.10 三阶段落地计划

| 阶段 | 内容 | 周期 | 验收 |
|---|---|---|---|
| **C1 · 用量速查** | 规则表 + `ComplianceEvaluator` + `POST /api/compliance/usage` + 前端输入框 | 3-5 天 | 28 条自动抽取规则入库并**人工校核**；输入「维生素C+猪+200mg/kg」返回合规+原文；输入 500 返回超限+超出量；输入未覆盖物质返回 **not_covered** |
| **C2 · 配方审查** | 批量入参（配方成分表）+ 物质目录表 + 禁用清单 | 5-8 天 | 上传 10 行配方 → 输出逐成分风险报告；禁用成分标红并给出依据条款 |
| **C3 · 标签审查** | GB 10648 强制标示项抽取 + 标签文案检查 | 5-8 天 | 输入标签文案 → 输出缺失项/违规宣称清单，每项带条款出处 |

> **C1 是快档方案的核心** —— 构想稿里最有说服力的场景（「预混料添加量合规吗」）
> 在 C1 就能跑通。

## 5. 功能三：风险预警模块（10%）

**这是四个模块里数据缺口最大的**。三类预警，三种不同的数据需求。

### 5.1 法规变更预警

```
农业农村部官网 / 国家饲料质量检验中心
        │
        ▼  公告监测爬虫（每日定时）
        │
        ▼  变更检测 → 增量更新向量库 + 图谱 + 规则引擎
        │
        ▼
  影响分析 → 向订阅用户推送预警
```

**构想稿的流水线设计是对的**，落地对应：

| 阶段 | 落地 | ADR-004 归属 |
|---|---|---|
| 爬虫 | Cloudflare Cron + 爬虫适配器 | ⑤ 法规监测 |
| 变更检测 | 新旧文档文本 diff | ⑤ |
| 增量更新 | 事件 `RegulationReleaseDetected` → ① 知识库 | ⑤ --事件--> ① |
| 规则重算 | 事件 `RegulationVersionIngested` → ② 合规规则 | ① --事件--> ② |
| 影响分析 | `RulesRecalculated` → ⑤ | ② --事件--> ⑤ |
| 推送 | 订阅 + 简报生成 | ⑤ |

> **ADR-004 的领域事件契约已经定义好了**（`domain/shared/domain-event.ts`），
> 这条流水线不需要重新设计架构，只需填实现。

**可行性关键**：政府网站结构 → 爬虫**脆弱**（站点改版即失效）。
**对策**：
- 选择**稳定的 RSS/JSON 接口**（若有）优于解析 HTML
- 变更检测**不依赖精确 diff** —— 用「文档指纹 + 标题匹配」做粗粒度检测也可
- 爬虫失败必须**告警而非静默**

**周期**：4-6 周（M4），但**基础设施（事件契约）已就位**。

### 5.2 抽检结果预警

> 「接入国家饲料质量抽检数据，提示同类产品风险」

**数据源完全外部**：
- 国家饲料质量抽检结果由农业农村部定期发布（公告形式，PDF）
- **无 API**，需爬取或人工录入
- 粒度是「产品批次 + 检验结论」，**没有企业配方数据**，无法直接做「同类产品」关联

**可行性判断**：⚠️ **低**。

能做的是「公告检索 + 关键词匹配」，不能做「同类产品风险提示」——
后者需要企业的产品线数据（我们没有）。

**建议**：**降级为「抽检公告聚合检索」** —— 用户订阅「维生素C」，
抽检公告里出现该物质时推送。这是有价值且可实现的，但**与构想稿描述的语义不同**，
需要在产品文档里说清楚，避免期望落差。

### 5.3 合规日历

> 「提醒换证、年检、标准更新过渡期截止日期」

**数据可行性**：

| 类型 | 数据来源 | 可得性 |
|---|---|---|
| 换证/年检 | 企业自己的证件到期日 | ❌ 外部数据（企业系统） |
| 标准更新过渡期 | 标准文本里的「实施日期」条款 | 🟡 **语料里可能有** |

「过渡期」的技术形态：标准正文常写「本标准自 XXXX 年 XX 月 XX 日起实施，
代替 YYYY 版」。这在语料里可以正则抽取。

**可行性判断**：🟡 **部分可做**。

- 「标准更新过渡期」→ 语料抽取 + 日历视图，**能做**
- 「换证/年检」→ 需要企业侧数据，**做不了**

**建议**：第一期只做「法规/标准生效日期日历」，明确不含企业证件到期提醒。

### 5.4 小结

| 子功能 | 可行性 | 建议 |
|---|---|---|
| 法规变更预警 | 🟢 可做（4-6 周） | 按 ADR-004 M4 排期 |
| 抽检结果预警 | 🔴 语义要降级 | 改为「抽检公告聚合检索」，文档需说明 |
| 合规日历 | 🟡 部分可做 | 只做标准生效日期，不含企业证件 |

### 6.2 待补 ①：多轮追问（低成本高价值）

构想稿：「支持多轮对话追问 —— 先问限量、再追问某配方的合规性」

**当前状态**：`QAPage` 每次独立提问，无会话状态。

**设计**：

```
POST /api/qa/conversation
{
  "sessionId": "...",
  "question": "维生素C在猪饲料中的使用量上限是多少？"
}
```

**会话记忆的最简实现**（不引向量库）：

```sql
CREATE TABLE qa_sessions (
  session_id    TEXT PRIMARY KEY,
  created_at    TEXT,
  updated_at    TEXT
);

CREATE TABLE qa_messages (
  message_id    TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL,
  role          TEXT NOT NULL,      -- user | assistant
  content       TEXT NOT NULL,
  -- 本轮检索到的证据（供下一轮做指代消解）
  evidence_json TEXT,
  -- 本轮识别出的实体（下一轮可直接复用）
  entities_json TEXT,
  created_at    TEXT
);
```

**指代消解**：第 2 轮问「那鸡呢？」时，需要知道「那」指的是**维生素C**。

```ts
// 从上一轮提取的实体 + 当前问句，构造补充检索 query
export function resolveContext(
  previousEntities: ExtractedEntities[],
  currentQuestion: string
): string {
  // 若当前问句不含已知物质名，且有历史实体 → 补进 query
  const hasKnown = previousEntities.some(e =>
    currentQuestion.includes(e.substance));
  if (hasKnown || previousEntities.length === 0) return currentQuestion;
  return `${previousEntities[0].substance} ${currentQuestion}`;
}
```

> **成本很低**（一个 session 表 + 一次实体回填），但对用户体验提升明显。
> **建议列为 C1 的附带项**（1 天）。

### 6.3 待补 ②：复杂问题拆解后分步回答（Planner）

构想稿：「复杂问题拆解后分步回答」

**但这里有个判断题**：值不值得上 Planner（LangGraph / 状态机）？

| 考量 | 分析 |
|---|---|
| 当前问题类型 | 法规问答大多是**单跳检索**（找条款、找限量），Planner 收益低 |
| 真正的复杂问题 | 「帮我审查这个配方」→ 需要 意图识别 + 多步工具调用 |
| 但那个场景 | **属于合规审查模块**，应该走 `POST /api/compliance/*` 确定性接口，**不该走 LLM Planner** |
| 真正的 Planner 场景 | 「某原料能否用于猪饲料，同时要符合标签规定」→ 跨模块组合 |

**结论**：
- **合规审查场景不做 LLM Planner** —— 走确定性接口（§4.2）
- **跨模块组合查询才需要 Planner** —— 属于**低频高价值**场景，排在最后

**建议**：v1 **不做** Planner。在 M2 完成后，基于真实的复杂提问日志再决定。
> 这与 ADR-004 的「按需展开」原则一致 —— 不为不存在的需求建上下文。

### 6.4 待补 ③：答案结构化增强

构想稿期望「合规/不合规 + 依据条款 + 建议调整范围」这种结构化输出。

**但这是合规审查的输出格式，不是问答的输出格式**。问答应该保持
「直接答案 + 引用列表」，与当前实现一致。

**建议**：不要把两者混在一个 prompt 里。分开：
- `/api/qa` → 检索问答（已实现）
- `/api/compliance/usage` → 合规判定（§4.7）

## 7. 构想稿的「数据更新机制」设计评价

> 「这是关键难点」—— 构想稿的判断是对的。

**但它把三件事混在一起了**：

| 构想稿描述 | 实际是三件事 | 难度 |
|---|---|---|
| 「增量更新向量库」 | 文档版本入库 → 重建 embedding | 🟢 中等 |
| 「+ 图谱」 | 实体关系重抽 | 🟡 中等（且图谱当前是空表） |
| 「+ 规则引擎」 | **规则库重算** ← 真正的难点 | 🔴 高 |

**为什么规则重算最难**：

```
一篇新公告 → 哪些规则受影响？
  ├── 物质名匹配？     （别名映射，可能漏）
  ├── 条文号引用匹配？ （跨文档引用，需解析）
  └── 目录结构变更？   （新增/删除物质）
→ 判定「受影响」本身就是不确定的
```

**建议**：规则重算**分两阶段**：

| 阶段 | 做法 | 精度 |
|---|---|---|
| v1 | **物质名精确匹配** + 人工触发 | 会漏，但漏了只是「规则没更新」，不产生错误结论 |
| v2 | 加入跨条文引用解析 | 更全 |

> **关键**：漏更新规则 → 规则库滞后 → 但**不会产生错误结论**（因为判定依据的是当时的规则库），
> 加上 `rule_set_version` 就能审计。所以 v1 可以接受漏。

| 场景 | 构想稿描述 | 可行性 | 依据 |
|---|---|---|---|
| **企业品控人员** | 输入配方自动审查合规性，输出不合规成分及替代建议 | 🟢 **可做**（C1+C2） | 规则引擎 + 限量抽取 |
| **法规专员** | 订阅特定品类法规变更，获取影响分析报告 | 🟡 **部分**（M4 后） | 爬虫可做，但变更**影响分析**需规则库成熟 |
| **监管部门** | 批量审查企业标签标识，自动标注疑似违规项 | 🟡 **部分**（C3 后） | 标签规则可做；「批量」需企业标签数据 |
| **研发人员** | 查询新原料法规状态（是否在目录内、有无限量） | 🟢 **可做**（C1） | 目录表 + 规则表，一次查询 |

### 9.1 关于「替代建议」

构想稿说「输出不合规成分及**替代建议**」。

**替代建议需要一张「物质 → 可用替代品」映射表** —— 这是**新产品审定**的知识，
语料里**没有**（语料是法规，不是审定结论库）。

**建议**：
- v1 只给「该物质在 XX 动物下的允许区间」—— 这本身就是调整依据
- 替代品建议列为**待建数据源**，不要在文档里承诺

## 10. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| **规则抽取错误 → 错误结论** | **高** | ① `review_status` 闸门（未审核不参与判定）② 每条规则必绑 `source_article_id` ③ 每条规则保留原文摘录供人工复核 |
| **未覆盖被误判为合规** | **高** | `not_covered` 独立状态 + 单测锁死该分支 |
| 物质别名映射不全 | 中 | 三级匹配；不匹配就 `not_covered`，**不做模糊匹配**（抗坏血酸 ≠ 抗坏血酸钙） |
| 「款/项」粒度缺失 | 中 | 规则抽取在**条级**进行，一含多项的条文拆成多条规则，每条都标同一 `source_article_id` |
| 规则库随公告滞后 | 中 | `rule_set_version` + 结论绑定版本 + 「已修订」提示（M4 后） |
| 禁用清单假阳性 | 中 | 人工审核 + `review_status`；实例如「不得在生产过程中进行维修」不是物质禁用 |
| 组合约束被误当单体 | 中 | `rule_type='combination'` 独立类型，不参与单体判定 |
| 性能：每次判定查 D1 + 检索 | 低 | 规则库 v1 仅 30-50 条，全量载入内存即可 |
| 爬虫随政府网站改版失效 | 中 | 优先用 RSS/JSON 接口；解析失败告警而非静默 |

## 11. 需要业务方确认的事项

| # | 事项 | 我的建议 |
|---|---|---|
| 1 | **规则库 v1 的范围**：只做「添加剂用量」还是含「原料质量指标」？ | **只做添加剂用量**。原料目录的质量指标（蛋白质≥50%）语义完全不同，混在一起判定逻辑会崩 |
| 2 | **未覆盖时的产品行为**：阻断式还是提示式？ | **提示式 + 强制标注「需人工确认」**，不阻断（阻断会让用户绕开系统） |

| 6 | **LLM 私有化** | 维持公网；但 **C2 配方审查上线前必须重新评估**（配方是企业敏感信息） |

### 12.1 实测方法

```python
# 遍历 minimax/ 全部 .md
#   → 抽 <table> → 解析 <tr>/<td>
#   → 列宽一致性统计

```

### 12.2 关键实测结论

| 结论 | 数据 |
|---|---|
| 表格文件数 | 300 |
| 有效数据行率 | 89.1%（4291/4818） |
| 列宽一致的文件 | 256/300 = 85% |
| 限量三元组（格式感知） | **28 条 / 6 文件** |
| 朴素正则（非列感知） | 22 条 / 5 文件 → **漏抽多动物并列格式** |
| 关键词命中 | 标签 125 · 生产许可证 88 · 有效期 86 · 批准文号 65 · 禁用 39 · 休药期 23 |

### 12.3 为什么规则库 v1 只估 30-50 条

- 自动抽取得 28 条（仅《饲料添加剂安全使用规范》目录）
- 《饲料添加剂品种目录》23 个表格行可再抽一批
- 人工补充《饲料卫生标准》等文件的限量条款
- **v1 目标：50 条，覆盖 10-15 个常用添加剂**
- 后续靠 ⑤ 监测持续增量

> **不要追求 v1 就覆盖全量**。50 条规则能让 10-15 种常用添加剂的用量判定跑通，
> 这已经能验证整条链路（输入 → 判定 → 带原文引用）。覆盖度是运营问题，不是架构问题。
