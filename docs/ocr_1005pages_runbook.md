# 1005 页纸质书电子化 Runbook (手机拍照路线)

> 全部数字来自 2026-09-08 在本机 `E:/workspace/siliao` 的实测,不是估算。
> 硬件: RTX 2060 SUPER (GPU 不可用,见下) + PaddleOCR 2.7.0.3 / paddle 2.6.2 CPU。

## 0. 一句话结论

**手机拍照 + 本地 PaddleOCR 完全够用。1005 页 OCR 约 1.4 小时(CPU),
不需要买扫描仪、不需要修 GPU、不需要付费 OCR 服务。**
真正的风险不在识别率(单字准确率 92-100%),而在
**透视校正静默裁掉半页内容** —— 已修,并加了 QA 闸门防复发。

## 1. 拍摄阶段(唯一需要人力的环节)

时间成本: 1005 页 ≈ 500 次翻页,熟练后 **1.5-2 小时**。

要求(实测有效,别自作聪明改):

| 项 | 要求 | 为什么 |
|---|---|---|
| 分辨率 | 保持 1280x1707 左右即可 | 实测 2x 放大**没有**提升识别行数(6 页对照 -2 行),纯浪费时间 |
| 每张拍几页 | **单页拍摄**,不要一张拍两页 | 跨页表格拼接依赖单页边界 |
| 文件名 | `001.jpg` 起严格连号 | `qa_check.py` 靠连号查漏拍;哈希名(如 raw-pic/)无法查断号 |
| 光照 | 顶光、避免书页阴影 | 阴影会让 Canny 把阴影边当纸张边 → 透视校正裁错 |
| 压平 | 尽量把书压平 | 弯曲页的表格线断裂,x 聚类仍可用但行锚点会飘 |
| 关水印 | 关掉相机的"徕卡/机型"水印 | 否则要走 `remove_watermark` inpaint,残字污染 OCR |

分批策略: 每 100 页存一个目录 `raw/batch01/`...,拍完一批就跑一批,
不要 1005 页拍完才发现设置错了。

## 2. 流水线(4 步,已跑通)

```bash
cd E:/workspace/siliao

# 1) 拍照 → OCR → 单页 markdown  (含透视校正/水印/OCR缓存)
#    实测 33 页 = 2m45s → 5.0s/页 → 1005 页 ≈ 1.4h
.venv-ocr/Scripts/python.exe build/ocr/pic2md.py raw/batch01 <doc_id>

# 2) 质量闸门 —— 必跑!有 CRITICAL 就别往下走
.venv-ocr/Scripts/python.exe build/ocr/qa_check.py data/markdown/<doc_id>

# 3) 表格还原 (bbox x 坐标聚类还原网格, 含合并表头/单元格内换行)
.venv-ocr/Scripts/python.exe build/ocr/table_reconstruct.py \
    data/markdown/<doc_id> --out-sub pages_tbl --header '饲料法规文件'

# 4) 章节/条文切分 → 灌库 (沿用既有链路)
.venv-ocr/Scripts/python.exe build/ocr/article_splitter_ar.py ...
.venv-ocr/Scripts/python.exe build/export/seed_d1.py ...
```

调参不要重跑 OCR: `pic2md.py --from-cache` 直接复用 `raw_ocr/*.json`,省 3 分钟/轮。

## 3. 已修的坑(重要,别改回去)

### 3.1 透视校正静默吃掉半页 —— CRITICAL

`preprocess.py` 的角点检测会锁到**表格内边框**而不是纸张边缘:

- `058.jpg`: 1280x1707 → 1030x484,只剩 **23% 面积**,
  整个「表1 猪」+ 半个「表2 家禽」被裁掉。
  OCR 行数 **83 → 34**,「后备种用火鸡」整行凭空消失。
- 旧 guard 只看宽高比 `0.3 ≤ ratio ≤ 3.0`,而 1030/484 = 2.13 **合法通过**。
- 影响面: `feed-trial-guideline-2023` **14/33 页 (42%)** 中招。

修法: 加**面积守卫** `min_area_ratio=0.75`,面积保留不足就回退原图。
修复后实测: 058 → 83 行, 059 34→96 行, 049 34→81 行, 050 55→114 行。

> 教训: 图像预处理的降级判据必须用**面积**,宽高比检测不出"等比裁掉一半"。

### 3.2 PaddleOCR 默认抢 GPU 会崩批次

paddle 2.6.2 是 CUDA 11.8 编译版,本机是 CUDA 13.1 runtime,缺 `cudnn64_8.dll`
→ `PreconditionNotMet ... error code 126`,在 `predict_det` 阶段直接崩。

**必须显式 `use_gpu=False`**(已固化进 `pic2md.py:init_ocr`)。
不值得为此修 cuDNN: CPU 5.0s/页,1005 页 1.4h 已经够快。

### 3.3 表格切行不能用 y 中心聚类

同一表格行内各列文字 y 中心能差 36px(排版基线不齐),
而二级表头之间只差 42px —— **任何单一 y 阈值都无法同时"合并同行"和"分开表头"**。

y 投影空白带也不行: 058.jpg 育肥用火鸡(y=293-321) 与 种用火鸡(y=363-394) 之间
被「公:16(24)周龄」(y=319-354) 桥接,**没有空白带**。

最终方案: **以第一列(行标签列)为行锚点**,其余单元格按 y 落到最近锚点区间。

## 4. 当前能力与已知限制(诚实版)

实测 `feed-trial-guideline-2023` 33 页:

- QA 闸门: **CRITICAL=0 / WARN=0 PASS**
- 表格: 7 页含表,识别出 **15 个表格块 / 32 数据行**

做得好的:
- `058.jpg` 两个表 **完整正确**,含二级合并表头、单元格内 母/公 双行(`<br>` 合并)、
  以及此前丢失的「后备种用火鸡 | 出壳 | 30周龄 | 母:15<br>公:30 | 42天」
- 单字识别率 0.92-1.00,印刷体几乎无错字

**已知限制(需人工复核)**:
1. 一页 4 个表(如 059 的表3/4/5/6)时,行标签间距过密 →
   相邻行会被并成一行(059 表3 应 5 数据行,实得 2-3 行)。
   `detect_grid_rows` 的 0.35 阈值是对 058/059 调的,不同排版可能要重调。
2. 竖排文字未处理(本书是纯横排,暂不需要)。
3. 跨页表格拼接(`table_merge_pages`)**尚未实现** —— 目前跨页表按两个独立表输出。
4. 「泌乳奶牛/繁殖母牛」这类只在最后两列有值的行,可能掉出表格变成散行。

→ **建议**: 表格页(约占 20%)在灌库前用 `pages_tbl/*.md` 人工过一遍,
   1005 页里约 200 页有表,抽查比全量校对省 80% 时间。

## 5. 为什么不选其他方案

| 方案 | 否决原因 |
|---|---|
| 买平板扫描仪 | 1005 页压平扫描 ≈ 4-6h 人力,比手机拍照慢,且要额外花钱 |
| 手机 App(白描/扫描全能王) | 单页付费/限量,1005 页成本高;导出格式不可控,表格结构照样丢 |
| 云 OCR (百度/腾讯/阿里) | 1005 页要传敏感法规原文出网;按页计费;本地已够用 |
| MinerU (`run_mineru.py`) | 只吃 PDF,手机拍的是 JPG;且 MinerU 版面分析对翻拍畸变不如自研预处理稳 |
| 2x 超分后再 OCR | 实测 6 页对照 **-2 行**,零收益,+4% 耗时 |
| 修 GPU 跑 PaddleOCR | 要装 cuDNN 8 + 降 CUDA;CPU 1.4h 已够,收益不值风险 |
