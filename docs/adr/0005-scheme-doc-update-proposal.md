## 二、U1 · 第 7 章技术选型需要重写

方案文档第 7 章的选型表，7 项里 **5 项与实际落地不符**。

| 模块 | 文档推荐 | 实际落地 | 判定 |
|---|---|---|---|
| 智能体框架 | LangGraph / 自研状态机 | **无框架** —— 单 Worker 路由 + 手写编排 | ❌ 不符 |
| LLM | 国产合规大模型，**建议私有化部署** | MiniMax-Text-01 **公网 API**（DeepSeek key 402 余额不足） | ❌ 不符 |
| Embedding | BGE-M3 | BGE-M3（自建 Docker `ns.hbnongfengyuan.cn`） | ✅ 一致 |
| 向量库 | Milvus / Elasticsearch / pgvector | **都不是** —— D1 FTS5(trigram) ⊕ 外部 bge 服务 | ❌ 不符 |
| 规则引擎 | 自研 DSL + Python 执行器 | **零代码** | ❌ 未实现 |
| OCR | PaddleOCR | MiniMax API OCR + 自写表格重建脚本（`mm_table_*.py`） | ⚠️ 已换，效果达标 |
| 服务化 | FastAPI + Redis + PostgreSQL | **全换** —— Cloudflare Workers + D1 + Pages | ❌ 不符 |

### 2.1 更新要点

**(a) 服务化选型要写明「为什么偏离」**

这是最关键的一处。原选型假设自建服务器 + 关系库 + 长驻进程；实际选了 Cloudflare 全 Serverless。

> **偏离是受约束下的正确决策**，理由要写进文档：
> - 零运维成本（push 即部署，无服务器运维）
> - 零付费产品开通（R2 激活需人工接受条款 + 绑支付方式，API 绕不过）
> - 语料仅 7.3MB，D1 免费额度 5GB，正文存 D1 后 excerpt 从「20 次 R2 GET」变成「1 次 JOIN」
>
> **代价必须一并写明**：D1 FTS5 不是真正的向量库；无跨表事务；无长驻进程（规则引擎、爬虫这类重计算组件没有落点）。

**(b) 向量库那一行要改成「双路索引」的实测形态**

原写「向量库：Milvus / Elasticsearch」。实际是：

```
D1 FTS5 (trigram: phrase 优先 + bigram RRF + 标题加权 3x)
  ⊕
bge-m3 语义层 (自建 Docker, /v1/search)
  → RRF 融合(等权 1.0 : 1.0, K=60)
```

实测：业务 query MRR 0.488 → **0.717**（+47%），这是纯 FTS5 拿不到的。

**(c) 必须补一条「不引入 cross-encoder reranker」**

方案文档第 3.3 节写「双路索引……召回后统一重排序」。但 `evals/c_c_rerank_report.md` 的实测结论是**负面的**：

| 系统 | 正例 R@10 ≥50% |
|---|---|
| bge only | **57/78 (73.1%)** |
| bge + rerank | 49/78 (62.8%) **−10.3pp** |

根因：法规检索需要「同义条款识别 / 章节结构匹配 / 跨条款引用」，cross-encoder 对这些不敏感；且 query 是口语短问、text 是书面长条款，语义 gap 大。

> **这条负面结论必须写进选型表** —— 否则下一个开发者会照文档去加 rerank，把已经优化过的检索路径打回去。

**(d) LLM 私有化这条要标为「未达成 / 有条件」**

文档写「监管场景建议私有化部署」。实际是公网 MiniMax API。

**这是一个需要业务方拍板的合规问题，不只是技术选型问题**：
- 法规内容本身不涉密（已公开的法规原文），传公网 API 风险有限
- 但**用户提问可能涉及企业配方等敏感信息** —— 这个必须人工确认
- 若要求私有化，需要引入 GPU 服务器 + vLLM 推理，是**架构级变更**

### 2.2 更新后的第 7 章（建议稿）

| 模块 | **实际方案** | 备选 | 说明 |
|---|---|---|---|

## 三、U2 · 第 8 章实施路径需要标注进度

原表四期无进度标注，且验收标准**不可度量**。

| 阶段 | 文档周期 | 文档交付物 | 文档验收 | **实际状态（2026-10-28）** |
|---|---|---|---|---|
| 一期 知识底座 | 6–8 周 | 法规知识库 v1 + 双路检索 | 抽样问答引用准确率 ≥ 95% | ✅ **交付物超额完成**（196 文档/529 章/3145 条文；双路检索已上线）<br>⚠️ **验收标准未度量** —— 现有 eval 只有 retrieval 指标，无「引用准确率」口径 |
| 二期 问答与监控 | 4–6 周 | 问答 Agent + 变更监控 MVP | 内测用户满意度 ≥ 80% | 🟡 问答 Agent ✅ 已上线（流式 + 引用校验）<br>❌ 变更监控 **未开工**（无爬虫） |
| 三期 合规校验 | 6–8 周 | 规则库 v1 + 校验工作台 | 人工复核一致性 ≥ 90% | ❌ 未开工（规则引擎零代码）<br>→ **ADR-004 M2 正是这一期的技术落点** |
| 四期 审核与开放 | 4–6 周 | 材料预审 Agent + 开放 API | API 接入 ≥1 业务系统 | ❌ 未开工 |

### 3.1 更新要点

**(a) 补一列「实际状态」** —— 让文档成为**活文档**而非一次性方案。

**(b) 一期的验收标准必须换成可度量的口径**

「抽样问答引用准确率 ≥ 95%」目前**测不了** —— 现有 eval 是：
- `eval_minimax.py` → retrieval 指标（recall@10 / MRR / negative 精度）
- `eval_qa_faithfulness.py` → faithfulness

**没有「引用准确率」这个指标**。建议改为可自动化的口径：

```
引用准确率 = 答案中 valid:true 的引用数 / 答案中全部引用数
```

这个量在 `citation-validator.service.ts` 里已经能算出来（`hasOnlyValidCitations`），补一个 eval 脚本即可纳入 CI 门禁。

**(c) 里程碑周期要按「实际速度」重估**

一期原估 6–8 周，实际从 OCR 全量完成到生产上线用了约 3 周（ADR-003 记录）。**当前节奏比文档预估快**，二期/三期的周期应相应压缩。

## 四、U3 · 第 3 章知识库结构存在数据模型偏差

### 4.1 层级结构：文档说四级，实际三层

| 文档 | 实际 |
|---|---|
| 法规 — 章 — 条 — **款 — 项** | documents → chapters → articles（**三层**） |

**「款」「项」粒度未建模** —— 3145 条条文里的多项条款没有拆分。这有实际影响：

- 一条含多「项」的条文（如「本品适用于猪、家禽、水产，限量分别为 A、B、C」），
  **无法只引用其中一项** —— 引用粒度只能到整条
- 对 M2 的 `ComplianceEvaluator` 是硬约束：它需要「物质 × 动物 × 限量」三元组，
  而当前条文是「整条含多动物多限量」的表格文本

**建议**：M2 开工前，先做一次**限量表的结构化抽取**（这正是上轮建议的第 2 项），
把表格转成规则记录，而不是靠 LLM 从长条文里抽 —— 表格里的数字必须确定性地取。

### 4.2 单条记录字段：文档说 6 个，实际缺 4 个

| 文档要求的字段 | 实际 | 影响 |
|---|---|---|
| 条款正文 | ✅ `articles.body` | — |
| 发文机关 | ⚠️ 在 `documents.issuer`，**未下沉到条文** | 跨文档引用时需多一次 JOIN |
| 生效日期 | ⚠️ 在 `documents.effective_date`，**未下沉** | 同上 |
| **废止/修订状态** | ❌ **完全缺** | ⚠️ **影响「知识时效可审计」原则** —— 无法判断某条是否已失效 |
| **关联文件** | ❌ 缺 | 无法表达「第 X 条依据本条例第 Y 条」这类引用关系 |
| 术语标注** | ❌ 缺 | 术语归一化只能靠 embedding 近似 |

**「废止/修订状态」缺失是最需要补的** —— 它直接对应设计原则里的**「知识时效可审计」**，
也对应风险表里的「法规更新滞后导致过期结论」（应对措施是「过期版本答案自动加『已修订』提示」）。

**没有状态字段，这条风险的对策就无法落地。**

### 4.3 五类知识覆盖：实际语料比文档更宽

文档列的五类 vs 实际语料顶层目录：

| 文档类别 | 实际目录 | 文档数 |
|---|---|---|
| 法律法规 | `01法规` | 1 |
| 部门规章 / 规范性文件 / 目录与限量 | `02制度文件` | **139** |
| （文档未列） | `03相关法律法规文件` | **32** |
| 标准文档 | `04标准及标准目录` | 5 |
| （封面/目录） | `000封面` / `001目录` | 2 |

**注意**：`03相关法律法规文件` 32 份里包含《兽药管理条例》《新兽药注册办法》《兽药标签和说明书管理办法》等 —— **兽药类法规**。

> 这对架构有影响：方案文档第十章说本规范「可复用到其他垂直法规领域（如**兽药**、宠物食品）」。
> 但语料里**已经有兽药法规了**，只是挂在 `03` 目录下、没做领域标记。
> 如果要做「按领域切分」（饲料 vs 兽药 vs 宠物食品），
> 当前 `documents` 表**没有领域字段**，只能靠目录名硬编码。

**建议**：`documents` 表加一个 `domain` 字段（饲料/兽药/宠物食品/通用），
为「可复用到其他垂直法规领域」这个目标留出数据基础。

## 五、是否需要更新架构本身？—— 不需要

### 5.1 方案文档的架构与 ADR-004 高度一致

```
方案文档五层              →   ADR-004 限界上下文
├ 应用层                  →   (前端 + 开放API, 未建上下文)
├ 智能体核心层            →   ③ 问答 (仅问答 Agent; 校验/监控/审核 未建)
├ 能力层                  →   interfaces/acl + application/ + infrastructure/
├ 数据与知识层            →   ① 法规知识库 ✅ + ② 合规规则 (M2 待建) + ④ 图谱 (空壳)
└ 治理与安全(贯穿)       →   架构测试(13) + CI 门禁 + 引用校验
```

**ADR-004 五大上下文 = 方案文档四子智能体 + 知识库/规则库/图谱的落位**，没有冲突。

### 5.2 ADR-004 已经把方案文档的选型偏离记录在案

ADR-004 的「取舍」表明确写了：

> 全面迁移到 FastAPI + PostgreSQL + Milvus（**方案文档原选型**）→ **否决**
> 理由：放弃 Serverless 零运维优势

所以架构决策层已经闭环。**方案文档是「面向新读者的方案说明」，ADR 是「面向决策者的决策记录」，
两者定位不同 —— 方案文档应该更新成「与实际一致」的状态，但不需要推翻重来。**

### 5.3 唯一需要重新决策的一件事：LLM 私有化

这是**唯一**可能触发架构级变更的点，其余都是文档对齐。

**决策项**：法规问答是否允许用户提问经公网 LLM（MiniMax）发送？

| 选项 | 成本 | 风险 |
|---|---|---|
| **A. 维持公网 API** | 0 | 用户提问可能含企业配方等敏感信息 → 泄漏到第三方 |
| **B. 私有化部署** | 需 GPU 服务器 + vLLM（改造 `llm.acl.ts` 换 base_url，**代码层面成本低**） | 运维成本 + GPU 利用率；单卡可跑 7B/14B 量化模型 |
| **C. 分级**：法规通用问题走公网，企业敏感问题走私有 | 最高 | 需要问题分类路由 |

**我倾向 A（维持公网）+ 明确的用户侧提示**，理由：
- 本系统的输入是「法规查询」，不是「配方上传」—— 敏感数据场景属于 M3 的校验工作台，不在当前问答链路
- 若 M3 要上传企业配方，**那时必须同步做私有化**，且这与 M3 的合规校验是同一个决策包

> 但这是**业务方的合规判断**，不是我的技术判断 —— 需要拍板。
