6检索链路（FTS5 + bge hybrid）

query→ escapeFts→ A档 phrase+ B档 bigram→ RRF 融合+ bge 语义→ RRF 二次融合→ D1 JOIN 取正文→ plainExcerpt

三路召回

路径策略作用
A 档 · phrasequery 整句当 phrase 查，BM25 rank 天然最靠前高精度。「本条例所称饲料」整句 MATCH 命中 rank 1，纯 bigram 排不进 top20
B 档 · bigram RRFquery 切重叠 bigram → 每 gram 单独查 → RRF 融合 + 标题加权 3x高召回。长 query 整句必然 0 命中，只有这条路能出结果
bge-m3 语义POST /v1/search，score 降序取 rank近义表达兜底。业务 query MRR 0.488 → 0.717

三个关键参数（扫参结论，别乱改）

参数值理由
RRF K60原 RRF 论文推荐值
FTS : BGE 权重1.0 : 1.0实测扫参：w=0.7 → MRR 0.645；w=1.0 → 0.647。bge 权重太小命中被挤出 top20，太大稀释精确短语
标题加权3.0查询常直接点名法规（「新兽药注册办法」就是文件名），标题命中是强信号
⚠️ 不引入 cross-encoder reranker 实测（evals/c_c_rerank_report.md，86 用例）：bge only 57/78 (73.1%) → bge + rerank 49/78 (62.8%)，−10.3pp。
根因：法规检索需要「同义条款识别 / 章节结构匹配 / 跨条款引用」，cross-encoder 对这些不敏感； 且 query 是口语短问、text 是书面长条款，语义 gap 大。

分档的必要性

A 档与 B 档不能混在一个分数池 phrase 命中（精确）vs 只命中一个常见 bigram 的文档，精度差一个数量级。 实测混池时 phrase 命中的目标被挤到 top20 外；分档后全部回到 rank 1。

7问答链路（SSE 流式）

POST /api/qa→ 检索→ meta 事件→ LLM stream→ chunk 事件 ×N→ 引用校验→ done 事件
SSE 事件载荷时机
meta{ question, retrieval }检索完成后，先给用户看证据
chunk{ delta }逐 token 推送
done{ citations }流结束后做引用校验
error{ message }任何环节异常

引用校验 —— 「合规优先」的技术落点

CitationValidator 从答案里提取 [N]，与检索证据逐条对账： N 对应第 N 条证据 → valid: true；N 越界 → valid: false（前端标红，LLM 编造）。

领域服务而非工具函数 「答案里的每条引用都必须能落到真实条文上」是业务规则，不是技术细节 —— 它来自方案文档的「合规优先」原则，决定一个答案能不能对外发布。 所以它在 domain 层，纯函数，零 I/O，100% 可单测。

另提供 hasOnlyValidCitations() 作为显式发布闸门：无引用即不合格。供 M2 与未来审核流使用。

prompt 的行为准则

  • 必须只基于检索证据回答，不引用未在证据中出现的条文
  • 证据不足 → 直接回复「未找到相关规定」，不编造
  • 引用用 [N] 格式，不写「第一条」这种裸引用
  • 证据限 8 条 —— 过长会稀释 LLM 注意

关键设计：mock / 生产双模式

⚠️ 生产构建必须显式 VITE_USE_MOCK=false 否则线上页面会加载 mock 语料（3.2MB）并展示离线数据，看起来「能用」但其实没连 Worker。 用 import.meta.env.VITE_USE_MOCK 在 build 时内联，运行时改不了。

mock 模式的 QA 也**真的走检索**（mockApi.search），不是塞空 retrieval —— 否则 QA 页永远显示「当前 0 条证据」，e2e 只能断言一句废话。

两个必须记住的实现细节

① url.pathname 不做 percent-decode 中文 article_id 会带着 %E5%B0%81... 进 D1，查不到任何条文。 路由捕获到的参数必须 decodeURIComponent()。

② QA 的字段名：body 用 {q}（别名 question / ask）。 字段名写错时静默返回「未找到相关规定」—— 看起来像检索没召回，实际压根没收到问题。已改为明确报 400。
