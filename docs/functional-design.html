把《面向饲料法规的智能体.docx》的构想落到可排期的功能。 每一项都给出真实数据基础与可行性实测—— 限量表实测抽出 28 条三元组，表格结构 85% 列宽一致。 结论：构想稿是对的，但实现顺序应该是「先做能做的，再做需要新数据的」。

一句话判断 构想稿是对的，但它的实现顺序应该是「先做能做的，再做需要新数据的」。 法规检索与知识问答已上线；合规审查的核心（用量判定）现在就能做； 而版本追溯、抽检预警、合规日历都需要新数据源，不能靠现有语料变出来。

4功能二：合规审查模块（30%）

这是构想稿的核心价值主张，也是当前最大的能力缺口。

4.1 构想稿的原始设想

用户提问："这种预混料在猪饲料中的添加量合规吗？"

Step 1 意图识别  → 识别为"合规审查"，提取实体：产品类型=预混料、动物种类=猪、属性=添加量
Step 2 任务拆解  → 子任务1 检索适用条款 / 子任务2 查该动物阶段上限 / 子任务3 比对是否超标
Step 3 工具调用  → 向量检索 + 知识图谱 + 规则引擎
Step 4 结果融合  → 法规原文 + 阈值数据 + 比对结果
Step 5 输出生成  → 合规/不合规 + 依据条款 + 建议调整范围

4.2 落地映射 —— 每一步落到哪个组件

构想稿步骤落地实现状态
Step 1 意图识别POST /api/compliance/usage 的结构化入参替代 LLM 意图识别设计变更
Step 2 任务拆解单步判定，无需 Planner（一个物质×一个动物 = 一次比对）✅ 简化

4.3 关键设计变更 ①：不用知识图谱查「是否在目录内」

构想稿说「调用知识图谱：查询该产品是否在《饲料添加剂品种目录》中」。

「L-抗坏血酸(维生素C)」 ∈ 《饲料添加剂品种目录》

《饲料添加剂品种目录》在语料里是 02制度文件/04_（四）使用管理/45_饲料添加剂品种目录/， 含 23 个表格行。抽成一张 substance_catalog 表后，一次 SQL 精确匹配即可。

为什么不用图谱 图谱解决的是多跳关系推理（A→B→C）。「查某物质在不在目录里」是单跳集合查询， 上图谱是杀鸡用牛刀，而且图谱当前是空表（entities 实测为空）。
保留图谱的价值在于：跨法规的交叉引用关系（如「本条依据《条例》第X条」）， 那是审核预审场景的需求，不是用量判定。

4.4 关键设计变更 ②：意图识别改为结构化入参

走 LLM 的问题走结构化接口的问题
「预混料」是产品类型还是物质名？LLM 可能抽错入参就分好了字段
「200」是 mg/kg 还是 g/kg？LLM 会猜单位是必填字段
抽错了用户看不出来，还以为得到了结论参数错直接 400 报错
这正是「规则与模型双轨」的落地 量化硬约束用确定性规则引擎，语义判断用 LLM，二者冲突时以规则为准。 用量判定必须是确定性接口 + 确定性判定。LLM 只在用户不知道自己要查什么时帮忙 （自然语言 → 建议查询），不参与判定本身。

4.6 领域服务：ComplianceEvaluator

// domain/compliance/compliance-evaluator.service.ts

export type VerdictStatus =
  | "compliant"      // 合规
  | "exceeded"       // 超限
  | "prohibited"     // 禁用
  | "not_covered";   // ⚠️ 规则未覆盖 —— 必须显式出现

export interface ComplianceVerdict {
  status: VerdictStatus;
  ruleHits: RuleHit[];
  suggestion?: {
    maxAllowed: number;
    unit: string;
    message: string;
  };
  coverageGap?: {
    reason: string;
    relatedArticles: RelatedArticle[];
  };
}

export interface RuleHit {
  ruleId: string;
  sourceArticleId: string;
  sourceDocId: string;
  sourceExcerpt: string;
  limit: { min?: number; max?: number; unit: string };
}
export function evaluate(
  usage: UsageDeclaration,
  rules: ComplianceRule[],
  catalog: SubstanceCatalog | null
): ComplianceVerdict {
  // 1. 禁用规则优先 —— 禁用是硬红线, 无条件拒绝
  const prohibition = rules.find(r =>
    r.rule_type === "prohibition" && matches(r, usage));
  if (prohibition) {
    return { status: "prohibited", ruleHits: [toHit(prohibition)] };
  }

  // 2. 限量规则
  const limits = rules.filter(r =>
    r.rule_type === "limit" && matches(r, usage));

  // 3. ⚠️ 无命中 → 必须返回 not_covered, **禁止返回 compliant**
  if (limits.length === 0) {
    return {
      status: "not_covered",
      ruleHits: [],
      coverageGap: {
        reason: "规则库未覆盖该物质/动物组合, 需人工确认",
        relatedArticles: [],
      },
    };
  }

  // 4. 比对 —— 取所有命中规则中最严的一条
  const strictest = limits.reduce((a, b) =>
    (b.max_value ?? Infinity) < (a.max_value ?? Infinity) ? b : a);

  if (usage.value > (strictest.max_value ?? Infinity)) {
    return {
      status: "exceeded",
      ruleHits: limits.map(toHit),
      suggestion: {
        maxAllowed: strictest.max_value!,
        unit: strictest.unit,
        message: `超出上限 ${usage.value - strictest.max_value} ${strictest.unit}`,
      },
    };
  }
  // 5. 低于下限
  if (strictest.min_value !== undefined && usage.value < strictest.min_value) {
    return { status: "exceeded", ruleHits: limits.map(toHit),
      suggestion: { maxAllowed: strictest.max_value!,
        unit: strictest.unit,
        message: `低于下限 ${strictest.min_value - usage.value} ${strictest.unit}` } };
  }

  return { status: "compliant", ruleHits: limits.map(toHit) };
}
不变量 1 规则未覆盖时必须返回 not_covered，绝不能返回 compliant
依据：「合规优先」+ 风险表「规则覆盖不全造成漏检」。
实现细节：evaluate() 里「无命中 → return not_covered」这一分支 必须有单测锁死，且用故意构造的未覆盖物质测。这类 bug 极容易在后续重构中被"优化"掉。
不变量 2 每条规则必须绑定 source_article_id，无出处不允许入库
依据：「涉及监管结论的输出必须可溯源（条款号+原文）」。

4.8 命名匹配策略（工程难点）

用户输入的「维生素C」与规则库里的「L-抗坏血酸(维生素C)」对不上。

级别策略示例
1精确匹配 name_cnL-抗坏血酸(维生素C) → 命中
2括号别名维生素C → 从 L-抗坏血酸(维生素C) 的括号里提取 → 命中
3别名表 substance_alias维生素C / Vitamin C / Ascorbic acid → 命中
 
export function matchSubstance(
  input: string,
  catalog: SubstanceCatalog[]
): { match: SubstanceCatalog; method: "exact" | "alias" | "fuzzy" } | null {
  // 1. 精确
  const exact = catalog.find(c => c.name_cn === input);
  if (exact) return { match: exact, method: "exact" };

  // 2. 括号内别名 —— 「L-抗坏血酸(维生素C)」的括号内容
  for (const c of catalog) {
    const m = c.name_cn.match(/[（(]([^）)]+)[）)]/);
    if (m && m[1] === input) return { match: c, method: "alias" };
  }

  // 3. 别名表
  const byAlias = catalog.find(c =>
    c.name_en?.toLowerCase() === input.toLowerCase());
  if (byAlias) return { match: byAlias, method: "alias" };

  return null;  // ⚠️ null → not_covered
}
不做模糊匹配 向量相似度匹配出来的「维生素C ≈ 抗坏血酸钙」在合规判定里是危险的 —— 抗坏血酸钙和抗坏血酸的限量完全不同。宁可说「未覆盖」，不可猜。

4.9 禁用清单（规则类型 prohibition）

从 39 个含「禁用」的文件抽取。典型条款形态（实测）：

✅ 「严禁在自配料中添加禁用药物、禁用物质及其他有毒有害物质。」

❌ 「不得在饲料生产过程中进行维修、焊接、气割等作业。」
      ↑ 这条不是禁用物质！是「生产操作禁令」
抽取时必须人工剔除假阳性 这正是 review_status 字段存在的理由： 自动抽取 → 人工审核 → 才能生效。

未审核的规则不参与判定 —— 这是防止「正则抽错了直接给用户错误结论」的关键闸门。 
自动抽取候选 ──→ review_status='pending'
      │
      ├── 人工审核 ──→ 'reviewed' (生效) / 'rejected' (剔除)
      │
      └── 判定时只读 review_status='reviewed' 的规则

4.10 三阶段落地计划

阶段内容周期验收
C1 用量速查 规则表 + ComplianceEvaluator + POST /api/compliance/usage + 前端输入框 3-5 天 28 条自动抽取规则入库并人工校核；输入「维生素C+猪+200mg/kg」返回合规+原文；输入 500 返回超限+超出量；输入未覆盖物质返回 not_covered
C2 配方审查 批量入参（配方成分表）+ 物质目录表 + 禁用清单 5-8 天 上传 10 行配方 → 输出逐成分风险报告；禁用成分标红并给出依据条款
C3 标签审查 GB 10648 强制标示项抽取 + 标签文案检查 5-8 天 输入标签文案 → 输出缺失项/违规宣称清单，每项带条款出处

5.2 抽检结果预警

可行性：低 抽检结果由农业农村部定期发布（公告形式，PDF），无 API，需爬取或人工录入。 粒度是「产品批次 + 检验结论」，没有企业配方数据，无法直接做「同类产品」关联。

建议降级为「抽检公告聚合检索」—— 用户订阅「维生素C」，抽检公告里出现该物质时推送。 这有价值且可实现，但与构想稿描述的语义不同，需要在产品文档里说清楚，避免期望落差。

5.3 合规日历

类型数据来源可得性

「过渡期」的技术形态：标准正文常写「本标准自 XXXX 年 XX 月 XX 日起实施，代替 YYYY 版」—— 这在语料里可以正则抽取。

建议 第一期只做「法规/标准生效日期日历」，明确不含企业证件到期提醒。

6.2 待补 ①：多轮追问（低成本高价值）

构想稿：「支持多轮对话追问 —— 先问限量、再追问某配方的合规性」。当前 QAPage 每次独立提问，无会话状态。

CREATE TABLE qa_sessions (
  session_id    TEXT PRIMARY KEY,
  created_at    TEXT,
  updated_at    TEXT
);

CREATE TABLE qa_messages (
  message_id    TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL,
  role          TEXT NOT NULL,      -- user | assistant
  content       TEXT NOT NULL,
  -- 本轮检索到的证据(供下一轮做指代消解)
  evidence_json TEXT,
  -- 本轮识别出的实体(下一轮可直接复用)
  entities_json TEXT,
  created_at    TEXT
});
// 从上一轮提取的实体 + 当前问句, 构造补充检索 query
export function resolveContext(
  previousEntities: ExtractedEntities[],
  currentQuestion: string
): string {
  // 若当前问句不含已知物质名, 且有历史实体 → 补进 query
  const hasKnown = previousEntities.some(e =>
    currentQuestion.includes(e.substance));
  if (hasKnown || previousEntities.length === 0) return currentQuestion;
  return `${previousEntities[0].substance} ${currentQuestion}`;
}
建议列为 C1 的附带项（1 天） 成本很低（一个 session 表 + 一次实体回填），但对用户体验提升明显。

6.3 待补 ②：复杂问题拆解后分步回答（Planner）—— 暂缓

考量分析
当前问题类型法规问答大多是单跳检索（找条款、找限量），Planner 收益低
真正的复杂问题「帮我审查这个配方」→ 需要 意图识别 + 多步工具调用
但那个场景属于合规审查模块，应该走 POST /api/compliance/* 确定性接口，不该走 LLM Planner
真正的 Planner 场景「某原料能否用于猪饲料，同时要符合标签规定」→ 跨模块组合（低频高价值）
结论 合规审查场景不做 LLM Planner —— 走确定性接口。
v1 不做 Planner。在 M2 完成后，基于真实的复杂提问日志再决定。
这与 ADR-004 的「按需展开」原则一致 —— 不为不存在的需求建上下文。

6.4 待补 ③：答案结构化增强 —— 不做

构想稿期望「合规/不合规 + 依据条款 + 建议调整范围」这种结构化输出。 但这是合规审查的输出格式，不是问答的输出格式。问答应该保持「直接答案 + 引用列表」。

不要把两者混在一个 prompt 里 /api/qa → 检索问答（已实现）
/api/compliance/usage → 合规判定（新建）

7构想稿「数据更新机制」的评价

构想稿的判断是对的 「数据更新机制（关键难点）」—— 它确实是整个系统最难的部分。

但它把三件事混在一起了：

构想稿描述实际是三件事难度
「增量更新向量库」文档版本入库 → 重建 embedding🟢 中等
「+ 图谱」实体关系重抽🟡 中等（且图谱当前是空表）
「+ 规则引擎」规则库重算 ← 真正的难点🔴 高

为什么规则重算最难

一篇新公告 → 哪些规则受影响？
  ├── 物质名匹配？     (别名映射, 可能漏)
  ├── 条文号引用匹配？ (跨文档引用, 需解析)
  └── 目录结构变更？   (新增/删除物质)
→ 判定「受影响」本身就是不确定的
阶段做法精度
v1物质名精确匹配 + 人工触发会漏，但漏了只是「规则没更新」，不产生错误结论
v2加入跨条文引用解析更全
关键：漏更新规则是安全的 漏更新 → 规则库滞后 → 但不会产生错误结论（因为判定依据的是当时的规则库）， 加上 rule_set_version 就能审计。所以 v1 可以接受漏。

10风险与应对

风险等级应对
规则抽取错误 → 错误结论高① review_status 闸门（未审核不参与判定）② 每条规则必绑 source_article_id ③ 保留原文摘录供人工复核
未覆盖被误判为合规高not_covered 独立状态 + 单测锁死该分支
物质别名映射不全中三级匹配；不匹配就 not_covered，不做模糊匹配（抗坏血酸 ≠ 抗坏血酸钙）
「款/项」粒度缺失中规则抽取在条级进行，一含多项的条文拆成多条规则，每条标同一 source_article_id
规则库随公告滞后中rule_set_version + 结论绑定版本 + 「已修订」提示（M4 后）
禁用清单假阳性中人工审核 + review_status；实例如「不得在生产过程中进行维修」不是物质禁用
组合约束被误当单体中rule_type='combination' 独立类型，不参与单体判定
性能：每次判定查 D1 + 检索低规则库 v1 仅 30-50 条，全量载入内存即可
爬虫随政府网站改版失效中优先用 RSS/JSON 接口；解析失败告警而非静默
