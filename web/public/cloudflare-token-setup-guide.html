配置 Cloudflare API Token
让自动部署不再因 token 过期而中断

本指南一步步教你创建一个永不过期的 Cloudflare API Token，替换掉当前会过期的 OAuth token， 并接入 GitHub Actions。完成后，git push 即可自动部署，无需人工干预。

1为什么要换 Token

现在 GitHub Actions 里的 CLOUDFLARE_API_TOKEN 存的是 wrangler login 拿到的 OAuth token。它有个致命特性：会过期。

过期后自动部署会失败，报错长这样：

Authentication error [code: 10000]
Invalid access token [code: 9109]
最坑的地方 这个报错看着像「权限不够」，实际是「token 过期了」。2026-10-27 部署时就在这上面绕了一圈， 以为是 secret 没配对、权限给少了。凭据问题的报错必须能一眼看出是过期还是缺权限，否则每次都要重新排查一遍。

换成一个 Dashboard 创建的 API Token 之后：

OAuth token（现在）API Token（换完）
有效期会过期 几个月后突然挂不过期 一直有效
创建方式本机 wrangler loginDashboard 网页点选
权限范围跟随 wrangler 的固定 scope 集自己勾选，最小权限
能否被本机程序创建—不能 必须手点（原因见下）
为什么不能脚本化创建 试过用 OAuth token 直接调 POST /accounts/{id}/tokens，返回 403 Unauthorized to access requested resource。 OAuth token 本身没有 account:api_tokens 权限，无法自我提权创建新 token —— 只能去 Dashboard 手点。

需要的权限（三项，一勾就够）

权限作用域为什么需要
Workers Scripts — EditAccount — Guoguoping@gmail.com's Account部署 Worker
Cloudflare Pages — EditAccount — 同上部署前端
Account Settings — ReadAccount — 同上读取 Account ID / 账户信息
为什么必须是 API Token, 不能用 wrangler OAuth token OAuth token 1 小时就过期, 而且它带不来任何好处:
• npx wrangler login 要开浏览器手动授权(headless 过不了 Turnstile)
• 试过用 refresh_token 自动续期 —— 但 Cloudflare 每次刷新都会轮换 refresh_token,旧的那个立刻失效(实测本地刷一次,secret 里那个就废了, CI 报 invalid_grant)
• 要正确用就得把轮换后的 token 再写回 secret,而回写需要额外 PAT (仓库的 GH_TOKEN 改不了 Actions secret)—— 链路太长, 回写失败本身就是新的失败点
TTL 留空的 API Token 没有这些问题: 不过期、权限最小、不需要刷新。
关于 D1 部署流程里 不会通过 API 写 D1 数据（D1 正文是用 push_d1_bodies.py 走 REST bound params 单独灌的， 一次性操作）。所以不需要 D1 写权限。如果你的 Key 模板里带了 D1 Edit 也可以留着，无害。

3在 Dashboard 创建 API Token

1打开 API Token 页面

登录 Cloudflare Dashboard，直达：

https://dash.cloudflare.com/profile/api-tokens

也可以从 Dashboard 右上角头像 → My Profile → API Tokens 进入。

2点「Create Token」

页面顶部有 Create Token 按钮，展开后选 Create Custom Token（自定义），不要选模板 —— 模板会带上一堆用不上的权限。

3填写基本信息
Token namesiliao-deploy
Permissions见上表三项（Workers Scripts:Edit / Cloudflare Pages:Edit / Account Settings:Read）
Account ResourcesInclude → Guoguoping@gmail.com's Account（选具体账户，不要选 All accounts）
Client IP Address Filtering留空
TTL (Time to Live)Leave blank（不过期）
关键 TTL 必须留空。如果填了有效期，到期后又是同一场事故 —— 除非你确定会定期回来续期。
4创建并保存 token

点 Continue to summary → Create Token。创建成功后 token 字符串只显示这一次。

立刻复制保存 关掉这个弹窗就再也看不到了。如果丢了，删掉重建一个即可，不用担心。

存到一个安全的地方（密码管理器 / 本地 .env）。不要粘到聊天窗口、issue 或 git commit 里。

4验证新 Token 可用

先在本机验证，别直接丢给 CI —— 本地能跑通说明 token 和权限都对。

# 把 token 填进环境变量(临时)
export CF_TOKEN="粘贴你的新token"

# 验证 1: 能不能读账户
curl -s -H "Authorization: Bearer $CF_TOKEN" \
  https://api.cloudflare.com/client/v4/accounts | head -c 300

# 验证 2: 能不能列出 Worker 脚本(验证 Workers Scripts 权限)
curl -s -H "Authorization: Bearer $CF_TOKEN" \
  https://api.cloudflare.com/client/v4/accounts/1b938cc261b000a03554b506985daabb/workers/scripts | head -c 300
返回含义
"success": true通过 可以进入下一步
"success": false + 9109token 无效 复制时少了字符 / 有多余空格
9109 Unauthorized 在验证 2缺 Workers Scripts 权限 回第 3 步补权限
9109 在验证 1token 完全无效 重新复制一遍
Windows 用户注意 本机如果开了代理（http://127.0.0.1:7897 之类），curl 可能被代理拦截。 验证失败时先试：curl --noproxy "*" ...，确认是不是本地网络问题而不是 token 问题。

5接入 GitHub Actions

现在要把新 token 替换掉 GitHub 里的旧值。仓库的 secret 只能覆盖写入，不能读取，所以你需要手上有新 token。

方式 A：网页（最简单，推荐第一次用）

1打开仓库 secret 设置

https://github.com/Guoguoping1008/siliao/settings/secrets/actions

2更新 CLOUDFLARE_API_TOKEN

找到 CLOUDFLARE_API_TOKEN 这一行 → 点 Update → 粘贴新 token → Update secret。

另一个 CLOUDFLARE_ACCOUNT_ID 保持不变（1b938cc261b000a03554b506985daabb）。

方式 B：命令行（需要 gh）

# 装 gh(没有的话: https://cli.github.com)
winget install GitHub.cli

# 登录
gh auth login

# 写入 secret(token 不进 shell 历史, 不进进程列表)
printf '%s' "$CF_TOKEN" | gh secret set CLOUDFLARE_API_TOKEN --repo Guoguoping1008/siliao

# 确认
gh secret list --repo Guoguoping1008/siliao

方式 C：不用 gh（本仓库实际用的方式）

用 GitHub API + libsodium sealed box 加密写入，token 不经过明文传输：

pip install pynacl

python - <<'PY'
import json, urllib.request, base64, subprocess
from nacl.public import SealedBox, PublicKey
from nacl.encoding import RawEncoder

REPO = "/repos/Guoguoping1008/siliao"

# 从 git credential 拿 GitHub token
out = subprocess.run(["git","credential","fill"],
    input="protocol=https\nhost=github.com\n\n",
    capture_output=True, text=True).stdout
gh = [l[9:] for l in out.splitlines() if l.startswith("password=")][0]

def api(path, method="GET", body=None):
    req = urllib.request.Request(
        f"https://api.github.com{path}",
        data=json.dumps(body).encode() if body else None, method=method,
        headers={"Authorization": f"Bearer {gh}",
                 "Accept": "application/vnd.github+json",
                 "Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        raw = r.read()
        return r.status, (json.loads(raw) if raw else {})

# 1) 取仓库公钥
s, pk = api(f"{REPO}/actions/secrets/public-key")
pub = PublicKey(base64.b64decode(pk["key"]))

# 2) 用新 CF token 加密
cf_token = input("粘贴新的 CF token: ").strip()
sealed = SealedBox(pub).encrypt(cf_token.encode(), encoder=RawEncoder)

# 3) 写入(成功返回 204, 空 body)
s, d = api(f"{REPO}/actions/secrets/CLOUDFLARE_API_TOKEN", "PUT",
    {"encrypted_value": base64.b64encode(sealed).decode(),
     "key_id": pk["key_id"]})
print("HTTP", s)
PY
三个容易踩的坑
  • 成功返回 204 No Content（空 body）—— 按 JSON 解析会报「期待 null」，要「有 body 才 parse」
  • 公钥是 raw bytes，必须 base64.b64decode 后包成 PublicKey 对象
  • 本机没装 gh 不是问题 —— 方式 C 完全替代

在 GitHub Actions 页面选 Deploy workflow → Run workflow → 分支选 deploy/c-b-hybrid → 运行。

或者本地推一个空提交触发：

git commit --allow-empty -m "chore: 触发部署验证 token"
git push origin deploy/c-b-hybrid

部署完必须回读 —— 退出码 0 不等于线上真的活了。

# 前端
curl -s -o /dev/null -w "%{http_code}\n" https://siliao-web.pages.dev/

# QA(应有答案 + 引用)

7故障排查

部署报 Invalid access token [code: 9109]

最常见原因：token 过期。如果还没换 API Token，按下面处理：

  1. 本机刷新：cd query/worker && npx wrangler login（弹浏览器，自动批准）
  2. 把新 token 写回 GitHub secret（第 5 节任一方式）

如果已经换成 API Token 了还报这个，检查：复制时有没有带空格/换行、token 有没有被截断。

本仓库已加预检 2026-10-27 给 deploy.yml 加了「预检 Cloudflare 凭据」步骤 —— 部署前先 curl /accounts，token 失效时直接报 「token 无效或过期 → 跑 wrangler login → 更新 secret」， 而不是让 wrangler 抛一堆看不懂的 9109。
Pages job 报 ENOENT: no such file or directory, open 'dist'

工作目录不对。wrangler pages deploy dist 必须在 web/ 目录下执行。

deploy.yml 里该 job 需要 working-directory: web，否则会在仓库根找 dist。

另外：必须在 web/ 下跑才能把 web/functions/ 打成 Pages Functions bundle —— 在根目录跑即使找到了 dist，API 代理也会丢。

CI 报 EBADPLATFORM 或 Missing: @esbuild/linux-x64 from lock file

三个跨平台坑，2026-10-26 全踩过：

  • win32-only 直接依赖 → Linux 上 npm ci 直接失败。只依赖 wrangler，让 workerd 自己用 optionalDependencies 挑平台二进制
  • esbuild 版本分叉 → vitest 拉 0.28.2、vite 拉 0.21.5，lockfile 里出现 23 个嵌套平台包且没标 optional。加 "overrides": {"esbuild": "0.21.5"}
  • Node 版本太老 → wrangler@4 要求 ≥22，jsdom@30 / undici@8 要求 ≥22.13。CI 的 node-version 全改 22
Worker 部署成功，但搜索 excerpt 全是空字符串

正文没取到。当前生产不依赖 R2，正文存在 D1 的 articles.body 列，所以：

  • 确认 D1 里 body 列有值：SELECT count(*) FROM articles WHERE length(body) > 0;
  • 确认 Worker 的 wrangler.toml 里的 database_id 和实际 D1 一致

这个症状历史上还有个经典成因：生产配置里注释掉了 R2 binding，本地也复用了同一份配置 → env.INDEX_BUCKET 是 undefined。现在靠两份配置（wrangler.toml / wrangler.local.toml）分开避免。

QA 返回 {"answer": "未找到相关规定", "retrieval": []}

先看 body 字段名对不对：接口认 {"q": "..."}。传 {"question": ...} 曾经会静默返回这个结果（看着像检索没召回，实际压根没收到问题）。

2026-10-27 已修：缺字段返回 400 missing_query，并接受 q / question / ask 三种别名。

如果字段名对但 retrieval 仍为空，那是检索层问题，去查 /api/search 同一 query 是否有结果。

本地 wrangler dev 起来但连不上 D1 / R2
  • 本地必须用 -c wrangler.local.toml，且里面 remote = false
  • 改完 R2/D1 配置要 干净重启（kill 旧进程），热重载不生效
  • 本地可能有多个 D1 SQLite 文件（database_id 改过会新建），要挑 dev server 正在读的那个
  • Vite 默认只绑 IPv6，localhost 通但 127.0.0.1 不通 → 用 --host 127.0.0.1
前端页面完全没样式（CSS 只有一百多字节）

检查 web/postcss.config.js 是否存在。缺它 → Tailwind 插件不加载 → @tailwind 指令原样输出 → 页面无样式。

这个坑很隐蔽：单元测试和 e2e 全绿也不暴露，因为它们只断言文本内容不看样式。验证方法：

curl -s https://siliao-web.pages.dev/ | grep -o 'assets/[^"]*\.css'
# 再看那个 CSS 的体积 —— 正常应 ~20KB, 146 字节就是坏了
